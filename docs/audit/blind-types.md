# Type Safety Audit — blind pass

Scope: Type Safety only. Findings are runtime/compile-time type mismatches —
places where a TypeScript declaration is not actually guaranteed by anything,
and the gap is exploitable by real data. Method: grepped `sql<`, `as any`,
`as unknown`, `@ts-`, `z.any(`/`z.unknown(`, `JSON.parse(`, and `!` assertions
across `src/`, then read each hit in context to judge whether the assertion is
verified by adjacent control flow (safe) or actually unchecked (a lie).

Priority order followed: `src/infrastructure/` → `src/domain/` →
`src/application/` → `src/server/` → `src/lib/` → `src/app/` →
`src/components/`.

---

- [FOUND] src/infrastructure/database/repositories/products/product.repository.ts:343 — unchecked `as` cast narrows unvalidated public tRPC string input to a 4-value union, then binds it against a Postgres enum column — one severity: medium.
  - `filters.gender` originates from `src/server/routers/public/products.ts:80`, where the input schema is `gender: z.string().optional()` on `publicProcedure.list` — reachable by anyone, unauthenticated, with no allow-list.
  - `buildFiltersConditions` does `eq(products.gender, filters.gender as "men" | "women" | "unisex" | "kids")` — the cast tells the compiler the value is one of four literals; nothing at runtime checks that.
  - `products.gender` is a Postgres `pgEnum` column. A request like `list({ gender: "foo" })` sends `"foo"` as a bound parameter compared against an enum column; Postgres rejects it with `invalid input value for enum gender: "foo"`, which is not caught anywhere in the call path (`ProductRepository.findAll` → `buildFiltersConditions` → `db.select()...where()`) and surfaces as an unhandled exception/500 instead of a clean validation error.
  - Contrast with `updateOrderStatusSchema.status` in `src/server/routers/admin/orders.ts:35`, which sources its Zod schema from the same enum used by the domain (`z.enum(ORDER_STATUSES)`) — that is the pattern this call site should have used (`z.enum(["men","women","unisex","kids"])`) instead of a bare `z.string()` plus a downstream cast.

- [FOUND] src/infrastructure/database/repositories/dashboard/dashboard.repository.ts:53,61,69,93,157,168 — `sql<number>\`COUNT(\*)\``with no`::int`cast and no`.mapWith`, so the declared type is `number`but the driver returns a`bigint`-as-`string` — severity: low (latent; every current consumer happens to coerce, but the inconsistency is real).
  - Postgres `COUNT(*)` is `bigint`; postgres.js hands `bigint` back as a JS `string` unless the SQL casts it or Drizzle's own `count()` helper (which does `.mapWith(Number)`) is used instead of raw `sql`.
  - The same file gets this right elsewhere — `count: sql<number>\`COUNT(\*)::int\``(line 196) and`sql<number>\`COUNT(DISTINCT ${orders.userId})::int\`` (line 205) — so the uncast sites are a real, demonstrated inconsistency, not a deliberate choice.
  - Concrete runtime value: `getMetrics()`'s `ordersResult.count` is `"7"` (string), not `7`. It flows through `orders: ordersResult.count || 0` into `DashboardMetrics.orders: number`, which is actually a string at that point.
  - What currently absorbs it: `MetricsCards.tsx:47` renders `` `${metrics?.orders || 0}` `` (template-literal, coerces either way); `getAnalytics()`'s `totalOrders` is only ever divided (`totalRevenue / totalOrders`) or compared (`> 0`), and both operators auto-coerce a numeric string. `SalesChart.tsx` and `RevenueTrendChart.tsx` copy `row.orders` into chart-data objects but never plot or arithmetically use that field today — so the lie is real but currently inert. A future change that does `.toFixed()`, `.toLocaleString()`, or a strict `===` comparison on any of these `count` fields will break silently.

- [FOUND] src/lib/cache.ts:60,91 and src/components/home/ServerHeroSection.tsx:47, src/components/layout/ServerAnnouncementBar.tsx:33 — CMS content is read with a bare `JSON.parse` (implicit `any`) and then force-cast to a hand-written interface, bypassing the Zod schemas the codebase already has for exactly this data — severity: low-medium (degrades gracefully today, but trusts unvalidated DB content).
  - `getCachedHeroSection`/`getCachedAnnouncementSection` in `src/lib/cache.ts` return `parsedContent: JSON.parse(section.content)` with no type argument — this is `any`, not narrowed.
  - `ServerHeroSection.tsx:47` does `const parsed = heroSection.parsedContent as HeroContent;` and `ServerAnnouncementBar.tsx:33` does `const content = announcement.parsedContent as AnnouncementContent;` — neither call runs the row through `heroContentSchema`/`announcementContentSchema` or the existing `parseHeroContent`/`parseAnnouncementContent`/`safeParseSectionContent` helpers in `src/domain/site/value-objects/content-schemas.ts`, which were built for exactly this purpose and are used only on the admin **write** path (`src/server/routers/admin/settings/content-sections.ts`).
  - Concrete risk: a `content_sections` row written before validation existed, or restored via `revertToVersion` to an old history entry, or inserted by `pnpm seed` (which writes DB rows directly, not through the tRPC mutation), can carry a shape the interface doesn't match — e.g. `textAlignment` outside `"left"|"center"|"right"`, or `overlayOpacity` missing.
  - What currently absorbs it: both components wrap the read in `try/catch` and apply `?? default` almost everywhere, so a bad shape degrades (falls back to defaults or renders nothing) rather than crashing. The comment at `ServerHeroSection.tsx:61-65` explicitly acknowledges the gap for `ctaLink` ("no Zod parse on this path") and patches only that one field with `safeHref`; every other field (e.g. `textAlignment`, used as an object-key lookup at line 104) has no equivalent guard, so an out-of-union value there silently produces an `undefined` class fragment rather than a validation error.
  - Also note: the local `HeroContent`/`AnnouncementContent` interfaces hand-rolled in these two component files have drifted from the Zod-inferred `HeroContent`/`AnnouncementContent` types in `content-schemas.ts` (missing `backgroundVideo`, `ctaStyle`, `icon`, etc.) — two sources of truth for the same shape.

- [FOUND] src/infrastructure/database/repositories/wishlist/wishlist.repository.ts:67,69 — `products.basePrice as unknown as string` / `products.salePrice as unknown as string` — a double assertion through `unknown`, the strongest form of "trust me" — severity: low (currently a no-op; the value already is a string).
  - `basePrice`/`salePrice` are Drizzle `decimal()` columns, which `$inferSelect` already types as `string` (confirmed against the same columns used unassisted, e.g. `parseFloat(dbProduct.basePrice)` with no cast in `product.repository.ts:416`). The double assertion here is therefore redundant today, not a lie — but a double assertion through `unknown` is exactly the pattern that hides a real type mismatch if the query shape ever changes (e.g. a future `select({...})` that narrows or renames these columns), because `as unknown as X` defeats the normal "these types don't overlap" compiler check that a single `as X` would still give.

## Checked and found clean (worth recording so they aren't re-flagged)

- **Every other `sql<number>\`SUM(...)\``/`sql<number>\`COUNT(...)\`` site** (`cart.repository.ts:32,70,107,265,309`; `product-variant.repository.ts:239`; `wishlist.repository.ts:93`; `category.repository.ts:196`; `order.repository.ts:972,986`; `product.repository.ts:297`; `product-image.repository.ts:153`) is either explicitly cast with `::int` in the SQL or immediately wrapped in `Number(...)` before leaving the repository method. No lie reaches a caller.
- **`sql<string>` money aggregates** (`SUM_NET_REVENUE` in `dashboard.repository.ts` and `admin/customers.ts`) are honestly typed as `string` (matching Postgres `numeric` arriving as a string) and are consistently run through `parseFloat` at the boundary. Correct pattern.
- **Non-null assertions in `order.repository.ts`** (`a.variantId!`, `entry.item!`) at lines 313, 563, 703 are all preceded by a `.filter()` on the exact same predicate in the same expression chain — TypeScript can't carry the narrowing through the `.sort()`/next-step closure, but the runtime values are genuinely non-null at the assertion site.
- **`leftJoin` + `!` in `inventory.repository.ts:151-177`** (`r.productId!`, `r.productName!`, `r.productSlug!`) looked like a classic left-join-can-be-null bug, but `product_variants.product_id` is `NOT NULL` with `ON DELETE CASCADE` to `products.id` (`schema.ts:280-282`), so the FK guarantees the join always matches; a variant referencing a nonexistent product cannot exist. The assertions are safe, if stylistically odd (an `innerJoin` would make the guarantee visible in the type without asserting).
- **`resolveOrderAddress`/`parseAddressSnapshot` in `order.repository.ts:102-136`** is the right pattern for a `jsonb` column: `snapshot: unknown` in, per-field `typeof x === "string"` checks, safe `OrderAddress | null` out. No assertion at all — used as a positive reference point against the CMS-content finding above.
- **`src/app/api/csp-report/route.ts`** casts an external POST body through `ViolationFields` (all fields `unknown`) but every field is re-validated with `typeof value === "string"` in `pick()` before use, and the whole parse is wrapped in `try/catch`. The `as` casts add no actual trust here.
- **`OrderStatus.create`/`canTransition`** (`order-status.value-object.ts:73,77,109`) cast to `OrderStatusValue` only after `.includes()` against the same literal list — verified, not asserted blindly.
- **Enum/union drift check**: `OrderStatusValue` (order-status.value-object.ts) and `UserRole` (user-role.ts) match their `pgEnum` counterparts exactly. `InventoryChangeType` in `adjust-stock.use-case.ts` is derived directly from `inventoryChangeTypeEnum.enumValues`, so it cannot drift. `paymentMethodEnum` has 5 DB values but application code only ever writes/reads `"stripe" | "cash_on_delivery"` against a `paymentMethod: string | null` field on `OrderEntity` — the entity itself is honestly typed `string`, so the narrower unions live only in checkout-input types that legitimately never see the other 3 values; not a lie.
- **No `any`, `@ts-ignore`, `@ts-expect-error`, `z.any()`, or `z.unknown()` found anywhere in `src/` (excluding test files).**
- `csp-report`, `stripe/route.ts` webhook metadata access, `site-config.repository.ts`'s `as SiteSettingsProps` casts (interface matches the table columns field-for-field), `auth-helpers.ts`'s `profile?.role as UserRole`, and `user-profile.repository.ts`'s `dbProfile.role as UserRole` are all redundant-but-harmless casts onto values already carrying the matching literal type from Drizzle's schema inference — not lies.
